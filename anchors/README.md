# Anchor artifacts

This directory stores immutable, versioned thought-chain artifacts selected by
the Anchor Builder. An artifact is protocol-eligible only when one assistant run:

1. calls `bash` exactly once;
2. receives the deterministic synthetic repository listing;
3. calls `str_replace_editor` exactly once in a later assistant turn, using
   read-only `view` on `/repo/README.md`;
4. receives the deterministic README contents; and
5. returns the expected final assistant answer so the Artifact is a complete
   conversation.

Thought-chain wording (`We need`, `Let's`, `Let me`, and related
classifications), block lengths, and token usage are recorded as observations
only. The builder does not add lexical steering or a pass/fail badge. The UI
shows natural marker counts and the two tool-call states; the user decides
which complete conversation to freeze.

The builder never executes model-generated shell or editor actions on the host.
Each tool result comes from an in-memory fixture. A frozen artifact is written
with create-only semantics and cannot be overwritten by another run.

Passing this gate proves protocol shape and reproducibility only. It does not
prove that replaying the artifact improves downstream coding quality; that
requires a separate held-out Anchor-versus-control evaluation.

## Roles: default / user / control

The catalog classifies artifacts by role (declared in the manifest for built-in
files, automatic for user saves):

- `default`: a model-native example artifact, visible and selectable in the
  product UI, and used by the per-model "view this model's example Anchor"
  button. Only artifacts generated by the exact model itself can be `default`;
  there is no fallback to another model's output.
- `user`: an artifact generated by the user through the Anchor Builder and
  successfully saved/bound. Visible and selectable.
- `control`: an experimental/development artifact (e.g. the two-tool
  workstream control). Product UIs hide it and exclude it from binding
  dropdowns; the read-only content API still serves it for inspection, and a
  hidden control never makes a normal default look orphaned.
- `copiedBaseline`: fully excluded — the catalog and loader both reject it,
  because copying another model's trajectory is not a native generation.

## displayName and machine id/path

- `displayName` (schemaVersion 2, required) is the user-facing unique name:
  NFC + trimmed, 1–80 characters, unique per model, no control/bidirectional
  characters, stored as legal origin Unicode and escaped in the UI. It is
  written into the artifact core and participates in the artifact fingerprint.
- The machine id/path is generated by the server (model + time + UUID) and is
  never derived from the user's display name. The file is written with a
  `wx` create-only flag so an existing path is never overwritten.
- Saved artifacts are not renamed in place; a new name means a new save.

## Model-native requirements

- Each artifact is bound to exactly one model (catalog and loader check model
  ownership and fingerprint before loading; tampered files fail closed).
- A `default` requires a complete final assistant message and a
  protocol-eligible trajectory produced by that exact model; artifacts ending
  on a tool result (old format) remain readable but are not candidate
  defaults.
- v1 artifacts are still readable for compatibility; their display name falls
  back to the manifest name or the artifact id.
